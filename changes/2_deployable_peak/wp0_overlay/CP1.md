**`load_features.py`.**
- **`load` (3 features):** trailing demand-side disk-head time over the last 10, 30 and 60 minutes.
  - It sums the artifact's own `service_time(1, #chunks)` over every GET request with t−L ≤ ts < **t** (strict, so requests at the same second are excluded).
  - It is normalised with the artifact's `st_to_util(·, sample_ratio, duration_s=L)·100`, i.e. utilisation %, the units of `PeakServiceTimeUtil1`.
  - The series is built once per process by `DemandLoad.from_trace()` with the artifact's own reader (`legacy_utils.read_processed_file`, GETs only, ~1 s) from the same trace file the trainer reads (`local_cluster.tracefilename`) and the simulator reads (`--trace`).
  - Lookup is `searchsorted` plus integer cumulative request/chunk counts, so window sums are exact in counts, and both sides call the identical function.
- **`tod` (2 features):** hour of day (UTC) as sin/cos.
- **`LoadAdaptiveThreshold`:** g(x) = clip((x/ref)^α, 0.25, 4) on the chosen trailing window. α is the shape parameter, and α<0 admits more under high demand.

**Checks of the series:**
- Against a naive per-request sum on 12,000 random lookups: max rel diff 7e-16 (`src/unit_load.py`).
- Its 10-minute window sums equal the frozen simulator's own per-window `service_time_nocache` on all 996 windows of both traces: max rel diff 6.7e-12, same peak window (`results/demand_vs_sim.json`).

## 5. Open issues and decisions for review (G3)

1. **GET-only demand.**
   - `load` counts GET requests only, i.e. the simulator's `service_time_nocache`, which is the no-cache counterpart of `PeakServiceTimeUtil1`.
   - PUT disk time is excluded (the training reader is GET-only by default, and PUT DT is not in the peak metric).
   - If the team reads "all requests" to include PUTs, this is a one-line change in `DemandLoad.from_trace` (`only_gets=False` plus PUT service time).
2. **One-line `train.py` plumbing** for `--pf-feat-subset` (§1). The alternative is to drop optional item 1.3.
3. **Artifact nondeterminism.** For WP2, retrain-to-retrain variance comes from `imap_unordered` episode order: split, tie order, and rare label flips at the boundary. G1-det shows that pinning it in our launcher makes frozen and overlay reproducible. For the 2×2 study, either keep the artifact's behaviour (as phase 1 did, ≥3 retrains) or use pinned mode with distinct seeds. This is a team decision; WP2 would use the artifact's behaviour unless told otherwise.
4. **Feature order must be canonical.** It is `meta+block+chunk+load+tod` (groups appended after the original ones), and the simulator asserts the model's column names.
   - The artifact's `LearnedAP._predict` silently drops 3 features from any 12-feature vector. A 12-feature subset such as `meta_nosize+block+load` therefore fails loudly (LightGBM feature-count error); do not use it.
5. **Prefetch features.** Training uses the episode's first access and serving uses every GET access. This is the artifact's own design for the metadata features, and we follow it. The obsolete `episode-predict` path in `eviction_policies.py` gets no load features; it is not used by the Fig 9 configurations.
6. **Adaptive threshold.** The defaults are ref = 20 util-% (≈ the traces' mean demand), a 10-minute window and clip [0.25, 4]. Only α is meant to be tuned; θ is re-converged to the target write rate as usual.
7. **First hour of the trace.** The trailing windows are truncated there (no history before the trace start). Training and serving see the same truncated values.
8. **Disk.** The training dumps (`results/g1*/dumps`, `results/parity/dumps`; ~7 GB) are git-ignored and can be deleted; they are regenerable.
